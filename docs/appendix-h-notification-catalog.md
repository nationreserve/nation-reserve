# Notification Catalog

**Version:** 1.0
**Status:** Authoritative Notification Specification

---

# Purpose

This appendix defines every major notification generated by RoboWorkPool, including:

- Trigger
- Recipient
- Delivery channel
- Priority
- User preference controls
- Retry behavior
- Escalation rules
- Audit requirements

The notification system must communicate important changes without overwhelming users.

---

# Notification Principles

Every notification should be:

- Actionable
- Timely
- Role-appropriate
- Traceable
- Deduplicated
- Secure
- Written in clear language

Notifications should tell the recipient:

1. What happened
2. What it affects
3. Whether action is required
4. What action to take
5. Where to view more information

Sensitive information should not be fully displayed in email, SMS, push previews, or lock-screen notifications.

---

# Notification Classes

Notifications are divided into two primary classes.

## Mandatory System Notifications

Mandatory notifications communicate events involving:

- Account security
- Financial transactions
- Robot operational failures
- Legal agreements
- Contract obligations
- Ownership changes
- Administrative enforcement
- Safety incidents

Users cannot completely disable mandatory notifications.

They may sometimes choose the delivery channel, but the platform must preserve at least one reliable delivery method.

Examples:

- Password changed
- Payroll completed
- Payment failed
- Robot offline
- Account suspended
- Ownership transfer initiated
- Contract cancelled
- Manufacturer API credential revoked

---

## Optional Preference-Based Notifications

Optional notifications include:

- General reminders
- Informational updates
- Noncritical activity summaries
- Product announcements
- Performance reports
- Queue movement summaries
- Marketing communications

Users may enable or disable these by category and channel.

---

# Supported Channels

RoboWorkPool should support:

- In-app
- Email
- SMS
- Mobile push
- Web push, if implemented later

In-app notifications should be the permanent notification record for authenticated users unless retention policy requires otherwise.

---

# Priority Levels

## Critical

Requires immediate attention.

Examples:

- Security breach warning
- Suspicious login
- Robot safety incident
- Payment account compromise
- Manufacturer credentials revoked
- System-wide operational emergency

Preferred delivery:

- In-app
- Email
- SMS
- Push

---

## High

Important and potentially time-sensitive.

Examples:

- Robot offline during active operation
- Payroll failed
- Invoice overdue
- Contract cancelled
- Maintenance required
- Heartbeat integration failing

Preferred delivery:

- In-app
- Email
- Push
- SMS when configured or operationally necessary

---

## Normal

Routine business activity.

Examples:

- Contract approved
- Payroll completed
- Robot activated
- Invoice generated
- Queue position updated

Preferred delivery:

- In-app
- Email
- Push where enabled

---

## Informational

No immediate action required.

Examples:

- Weekly operational summary
- Performance insights
- Product announcements
- Documentation updates

Preferred delivery:

- In-app
- Email where enabled

---

# Standard Notification Record

Every notification record should contain:

```text
Notification ID
Notification Type
Notification Version
Recipient User ID
Recipient Organization ID, if applicable
Priority
Mandatory or Optional Classification
Title
Message
Action Label
Action URL or Internal Route
Related Entity Type
Related Entity ID
Created Timestamp
Scheduled Timestamp, if applicable
Delivered Timestamp
Read Timestamp
Acknowledged Timestamp, if required
Delivery Channels
Delivery Status per Channel
Retry Count
Correlation ID
Expiration Timestamp, if applicable
```

# Mandatory Channel Rules

A user must maintain at least one verified channel for mandatory notifications.

At minimum:

- Verified email

High-risk users or organizations may also be required to configure:

- Verified phone number
- MFA device
- Designated operational contact
- Designated billing contact
- Designated security contact

Users may not disable in-app records for mandatory notifications.

---

# Organization Recipient Rules

Notifications should be delivered based on responsibility, not merely to every organization user.

Examples:

- Billing failures go to billing contacts and Company Administrators.
- Heartbeat integration failures go to Manufacturer Engineers and Manufacturer Administrators.
- Workforce coverage gaps go to Company Supervisors and Company Managers.
- Security alerts go to organization security contacts and administrators.
- Contract approval requests go only to users authorized to approve the contract.

Organizations should be able to configure escalation contacts without weakening mandatory delivery requirements.

---

# Deduplication

The system must avoid repeatedly sending identical notifications for the same unresolved condition.

A notification deduplication key should consider:

```text
Notification Type
Recipient
Related Entity
Incident or Condition ID
Configured Deduplication Window
```

Example:

A robot that remains offline should not generate a new critical SMS every heartbeat interval.

Instead, the system should:

1. Send the initial outage notification.
2. Send scheduled escalation reminders.
3. Send a restoration notification when connectivity returns.

---

# Bundling and Summaries

- Daily summaries
- Weekly summaries
- Operational reports
- Queue movement summaries
- Robot performance summaries

Critical and high-priority notifications should never be delayed for summary delivery.

---

# Retry Policy

Failed deliveries should use exponential backoff.

Recommended general sequence:

```text
Initial attempt

↓

1-minute retry

↓

5-minute retry

↓

15-minute retry

↓

1-hour retry

↓

Final failure workflow
```

Exact retry schedules may differ by provider and priority.

---

# Channel Fallback

For mandatory high-priority notifications, failed delivery should trigger an approved fallback channel.

Example:

```text
Push fails

↓

Email attempted

↓

SMS attempted if configured and authorized

↓

In-app escalation remains active

↓

Operations alerted if delivery is legally or operationally critical
```

---

# Delivery Statuses

Each notification channel should track:

- Pending
- Queued
- Sent
- Delivered
- Opened, if supported
- Failed
- Suppressed
- Retrying
- Permanently failed

Provider delivery status should not be treated as proof that a person read the message.

---

# Acknowledgment Requirements

Certain notifications should require explicit acknowledgment.

Examples:

- Critical safety incident
- Production API credentials revoked
- Contract cancellation during active operation
- Payroll adjustment above a defined threshold
- Account suspension
- Emergency system instruction

Acknowledgment must record:

- User
- Timestamp
- Notification
- Device or session
- Acknowledgment response
- Optional comment

Failure to acknowledge may trigger escalation.

---

# Escalation Rules

Critical incidents should support escalation paths.

Example heartbeat outage escalation:

```text
Robot Owner

↓

Hiring Company operational contact

↓

Manufacturer operational contact

↓

Platform Operations

↓

Security or executive escalation when systemic
```

The exact escalation path should depend on event type, duration, and operational impact.

---

# Quiet Hours

Users may define quiet hours for optional notifications.

Quiet hours must not suppress:

- Critical security alerts
- Active robot safety incidents
- Active-contract heartbeat failures
- Payment failures requiring immediate intervention
- Legal or compliance notices
- Emergency platform instructions

---

# Time Zones

Notifications should be displayed using the recipient's configured time zone.

All stored timestamps should use UTC.

Messages should clearly state the relevant local time when deadlines or scheduled actions are involved.

---

# Notification Templates

Templates should support:

- Versioning
- Localization
- Variables
- Channel-specific formatting
- Previewing
- Approval
- Rollback
- Testing

Template variables must be validated before delivery.

Missing required variables should prevent delivery rather than expose malformed or misleading messages.

---

# Security and Privacy

Notifications must not expose:

- Full bank account numbers
- Full tax identifiers
- API secrets
- Password reset tokens in message text
- Government ID images
- Complete payment card details
- Confidential robot diagnostic data beyond what the recipient is authorized to view

Notification action links should use secure, expiring, purpose-limited tokens where authentication cannot be required immediately.

---

# Audit Requirements

The platform must audit:

- Creation of mandatory notifications
- Delivery attempts
- Channel failures
- Escalations
- Acknowledgments
- Template changes
- Administrative resend actions
- Suppression decisions
- Preference changes affecting mandatory delivery
- Contact changes for financial, operational, or security notifications

---

# Administrative Controls

Authorized administrators should be able to:

- View notification delivery history
- Filter failures by provider or type
- Retry failed notifications
- Disable a malfunctioning template
- Preview templates
- Review escalation status
- See provider availability
- Configure system thresholds
- Issue emergency platform messages

Administrators must not silently alter or delete immutable delivery history.

---

# Event Integration

Notifications should generally be generated from events defined in Appendix F.

Example:

```text
heartbeat.robot.offline

↓

Notification policy evaluates severity and recipients

↓

robot.offline notifications created

↓

Channel deliveries queued

↓

Delivery events recorded

↓

Escalation begins if unresolved
```

Business services should not directly embed email or SMS logic.

---

# Acceptance Criteria

This appendix is complete when:

- Mandatory and optional notifications are clearly separated.
- Every primary role has a defined notification catalog.
- Recipients, priority, channels, and required actions are identified.
- Preference controls cannot disable essential security, financial, legal, or operational alerts.
- Deduplication, summaries, retries, fallbacks, acknowledgment, and escalation are specified.
- Notification delivery and administrative actions are fully auditable.
- Sensitive data is protected across all channels.
- Notifications are driven by platform events rather than tightly coupled business logic.
